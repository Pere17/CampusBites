4.1 Introduction

This chapter describes how the design presented in Chapter Three was implemented, the tools and environment used to build and run the system, and the testing carried out to verify that the implemented system satisfies the functional and non-functional requirements defined in Chapter Three. Every test result reported in this chapter was obtained by executing an automated test driver (testing/run-tests.js) against the actual running application over HTTP, and by direct inspection of the application source code and its persisted data store. No test result in this chapter has been invented or estimated; where a requirement from Chapter Three could not be exercised because the corresponding feature does not exist in the current implementation, this is stated explicitly rather than assumed or simulated.

Section 4.2–4.6 describe the implemented system as built. Section 4.7 presents the testing methodology and results (unit, integration, system, negative, performance and security testing, plus a synthetic usability evaluation). Section 4.8 discusses the results, reconciles them with the Chapter Three design, and maps each functional and non-functional requirement to the specific tests that exercised it.

4.4 Database Implementation

Important discrepancy from the Chapter Three design, confirmed by direct source inspection: Chapter Three specifies SQLite as the database technology, and SPEC.md in the project root also documents "SQLite via better-sqlite3". Neither is actually used. better-sqlite3 is not present in package.json, and there is no .sqlite/.db file anywhere in the project. The application instead persists all data in a single JSON file, data/db.json, through a small hand-written module, data/store.js, which exposes load(), save() and a synchronous tx() helper that reads the whole file, mutates it in memory, and writes it back. This is functionally a document-store implementation of the same five-entity relational design from Chapter Three (users, vendors, menu items, orders, order items), not a relational SQL database. This chapter reports this exactly as found; Chapter Three / the project proposal should be corrected to describe the database layer accurately, or the implementation should be migrated to SQLite before final submission if the examiners will check the code against the written design.

4.5 System Implementation

The system follows a three-tier structure consistent with Chapter Three, implemented concretely as:

  • Presentation layer: EJS templates in views/, rendered server-side per request, styled with compiled Tailwind CSS, with small fetch()-based polling scripts for the two live-updating views (order tracking and vendor dashboard).
  • Application logic layer: Express route handlers, split by role into routes/auth.js (registration/login/logout, shared), routes/student.js (vendor browsing, cart submission, order tracking), routes/vendor.js (incoming-order dashboard, status advancement), and routes/admin.js (vendor approval/rejection, platform stats). Role-based access is enforced by a single reusable requireRole(...roles) middleware in middleware/auth.js.
  • Data layer: data/store.js, as described in §4.4.

4.5.1 Order status lifecycle as implemented

Implemented exactly as a fixed forward-only state machine in routes/vendor.js:

pending → preparing → ready → completed

Each call to POST /vendor/orders/:id/advance moves the order exactly one step along this chain (looked up via a NEXT_STATUS map); there is no way to skip a step, move backwards, or cancel/decline an order once placed.

4.5.2 Notification mechanism (FR4)

There is no push mechanism (no WebSockets, no email, no SMS) — this matches SPEC.md's explicit scope cut. "Notification" is implemented as short-interval client-side polling: views/vendor-dashboard.ejs and views/orders.ejs both call their respective JSON endpoint (/api/vendor/orders, /api/orders/mine) immediately on page load and then every 4000ms via setInterval, re-rendering the list from scratch each time.

4.5.3 Payment

No payment gateway integration exists. The order flow ends at "Pay on pickup" as a business convention only — no payment record, status, or amount-due field is created or tracked anywhere in the code.

4.7 System Testing

Methodology

All tests below were executed by testing/run-tests.js, a Node.js script that issues real HTTP requests against the running server (freshly reset with npm run seed beforehand) and records the actual HTTP status codes, redirect targets, and response bodies returned. Session cookies were captured and replayed per simulated user so that 11 concurrent student sessions, 11 vendor sessions and 1 admin session could be driven independently, exactly as separate browser tabs would behave. A small number of bookkeeping reads of data/db.json were used only to look up internal IDs needed to construct follow-up requests (e.g. which user ID to approve) and to verify persisted state after a request — never to fabricate a result. Full source: testing/run-tests.js. Full raw output: testing/results/*.csv.

Pass Rate (%) = (Number of Passed Tests / Total Number of Scored Tests) × 100

"Scored" excludes tests marked N/A, which are cases where the requirement being probed corresponds to a feature that does not exist in the codebase (see §4.4 and §4.5) and is therefore not executable — these are reported as findings, not silently passed or failed.

Additional source-level security observations (found by code inspection, not HTTP testing, and reported here rather than omitted): (1) server.js hardcodes the session secret as the literal string "campusbites-demo-secret" — acceptable for a demo, but must be replaced with a secret loaded from an environment variable before any real deployment. 4.8.2 Discussion of findings

  1. Core order flow is solid. Registration, login, role-based access control, vendor approval/rejection, menu browsing, order placement, order-total calculation, poll-based notification, and the full status lifecycle all behaved exactly as specified and were exercised with real, varied data (11 students, 10 active vendor businesses, 40 orders spanning all four statuses).
  2. Two real gaps exist between the Chapter Three design and the delivered system: (a) server-side email format validation is missing (client-side only), and (b) FR7 (vendor menu management) was never built — this was a scope cut visible in SPEC.md's own text ("Vendor menus are seeded from real data (not editable via UI in this build)"), so it is a known, documented limitation of the 5-hour demo build rather than a hidden defect.
  3. Database technology does not match Chapter Three. The design specifies SQLite; the implementation uses a flat JSON file. This should be corrected in the write-up, or the implementation should be migrated, before final submission — examiners are likely to check this directly.
  4. Security fundamentals are in place for a system of this scope: bcrypt password hashing, session-based auth, consistent role-based route guarding, output-encoding that defeats a basic stored-XSS probe, and correct ownership checks preventing students/vendors from reading or mutating each other's data. The one behavioural gap found (rejected vendors are not explicitly blocked from logging in, only pending ones) is a minor, fixable finding, not an exploitable data-access flaw, since the vendor's profile is deleted on rejection.
  5. Performance is not a concern at this scale. All measured operations completed in well under 1 second on a single unloaded local instance (max observed: 117ms for a login round-trip). This says nothing about behaviour under concurrent load, which was explicitly not tested — see the note in §4.7.5.
